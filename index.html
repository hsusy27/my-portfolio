系統定位

一般投資人或產業分析師在研究台灣半導體供應鏈時，常遇到三個問題：每日股價與每月營收資料（公開資訊觀測站 MOPS）散落在不同平台，難以即時交叉比對；市面看板多以單一個股呈現，缺乏「上游 IC 設計 → 中游晶圓代工 → 下游封測 → 設備材料」的供應鏈巨觀視角；介面資訊層級混亂，關鍵數字沒有被階層化呈現。

這個專案的目標是做出一套端到端的 BI 看板：資料從擷取、清洗、正規化建模到前端呈現全部自己掌控，而不是把現成資料丟進一張大表格就結束。

系統架構（四層）

  1. Data Source Layer：yfinance API（股價）、FinMind API / MOPS（月營收）
  2. ETL & Processing Layer：etl_pipeline.py，擷取 → Pandas 向量化清洗
  3. Storage Layer：SQLite 星型模型，Dim_Company / Fact_Daily_Stock / Fact_Monthly_Revenue
  4. BI Analytics & UI Layer：app.py，SQL 視窗函數運算 → CSS 客製注入 → Streamlit 儀表板
資料庫模型（星型模型）
資料表型態說明
Dim_Company維度表stock_id（PK）、company_name、sector（上游 IC 設計／中游晶圓代工／下游封測／設備材料）
Fact_Daily_Stock事實表複合主鍵 (stock_id, date)，開高低收、成交量、每日漲跌幅
Fact_Monthly_Revenue事實表複合主鍵 (stock_id, year_month)，月營收、MoM、YoY

一張維度表對兩張事實表都是 1 : N，個股的股價與營收各自以自己的時間顆粒度（日／月）獨立累積，查詢時再依 stock_id 關聯。

核心功能（依頁面模組）

首頁總覽（Home）
  • 跑馬燈式報價條：橫向捲動顯示所有個股最新收盤價與漲跌幅徽章（紅漲綠跌，符合台股慣例配色）。
  • KPI 卡片：當月半導體總營收，以及上／中／下游三個子產業的營收加總，一眼看出巨觀產值分佈。
  • 動態趨勢圖（同一張圖兩種模式）：下拉選單可切換「全產業總營收趨勢」（依 sector 分色的折線圖）或「個股 K 線」；選到個股時，K 線圖疊加 20 日與 60 日均線，均線透過 SQL 視窗函數即時算好再畫，不在前端用 Pandas 另外算一次。
  • 產業代表性個股表：卡片化列表，每列有色塊縮寫圖示、公司名／代碼、產業位置、收盤價、當日漲跌幅、營收 YoY。
  • 產業鏈產值結構占比（甜甜圈圖）：中空圓餅圖呈現四個產業區塊的營收占比，中心疊字顯示「100」，右側配色圖例逐項標示百分比。
  • 市場焦點手風琴（Market Focus）：依產業分組，用 HTML <details>／<summary> 做成可展開收合的清單，預設展開「上游 IC 設計」，每組列出成分股的即時報價，不需要額外的 JS 互動套件。

技術架構細節

  • 資料存取層：query_db() 統一封裝 sqlite3.connect + pandas.read_sql_query，並用 @st.cache_data(ttl=600) 快取查詢結果 10 分鐘，避免每次互動（切換下拉選單）都重新打資料庫。
  • SQL 端運算優先：均線（AVG() OVER (ORDER BY date ROWS BETWEEN N PRECEDING AND CURRENT ROW)）與「取每檔股票最新一筆」（ROW_NUMBER() OVER (PARTITION BY stock_id ORDER BY date DESC)）都寫成 SQL 視窗函數，由資料庫引擎算完才回傳給 Python，而不是撈全部資料回來用迴圈或 Pandas 逐檔計算。
  • 參數化查詢：個股查詢一律用 ? 佔位符搭配 params=(stock_id,) 傳入，不做字串拼接，天生避開 SQL Injection。
  • 視覺層：Streamlit 原生元件（st.metric、st.plotly_chart）之外，大量用 st.markdown(..., unsafe_allow_html=True) 注入自訂 HTML/CSS，做出 Streamlit 預設樣式做不到的圓角卡片、徽章、跑馬燈、手風琴等「SaaS 感」介面。
  • 色彩系統：SECTOR_COLOR_MAP 把四個產業分類固定對應到一組莫蘭迪色系色碼，同一套色碼同時用在折線圖、甜甜圖與清單色塊，確保全站視覺一致。

資安與工程風險評估

目前設計中「做得不錯」的地方：

項目說明
個股查詢採參數化 SQLFact_Daily_Stock WHERE stock_id = ? 用參數綁定，不是字串拼接，避免 SQL Injection。
星型模型分離維度與事實公司基本資料與逐日／逐月數據分表存放，更新股價不需要動到公司資料，降低資料異動時互相牽連的風險。
查詢結果具快取機制ttl=600 避免短時間內重複查詢打爆資料庫、也降低外部 API 呼叫頻率超限的風險。
ETL 與 UI 分層資料擷取（etl_pipeline.py）與呈現（app.py）是獨立腳本，重新整理資料不需要重啟或改動前端程式。
資料本質為公開資訊股價、月營收皆為公開資訊觀測站資料，不涉及個資或機敏資料，資料本身的洩露風險低。

系統定位

這是一套給中心人資承辦人使用的新聘人員資格初審工具。傳統上，需「手動」把應徵者履歷內容一條一條比對該職位的進用門檻（學歷、年資、成果件數等），符合的話也需要手寫簽呈公文。此系統把「比對」跟「寫公文」兩件事自動化，人資只要輸入／上傳資料、按一個按鈕即可比對條件並生成相關聘任公文。

核心功能（依操作流程）

STEP 1｜選擇職位與門檻規範
  • 下拉選單內建 17 種常見職位（研發工程師、演算法工程師、資料科學家、法規品管工程師、專案經理等各職等），選擇後自動帶出該職位的學歷／年資／成果門檻文字範本。
  • 也可選「自訂」，手動輸入院內特殊的審核條款。
STEP 2｜輸入應徵者資料
  • 基本資料：姓名、擬聘單位、聘任類別（院聘／計畫聘，兩者對應不同經費支應文字）。
  • 履歷摘要文字框：可手動輸入，也支援人資自行補註「已確認具備 5 年工作經驗」等說明，AI 會直接採信這類人工確認的文字。
  • 檔案上傳與解析：支援拖曳或點擊上傳 PDF、TXT、圖片。
    • 文字型 PDF：用 PDF.js 在瀏覽器端直接擷取文字。
    • 掃描影像 PDF／圖片（如證照、推薦信掃描檔）：轉成 Base64，連同文字一起送給 Gemini 做視覺 OCR 辨識，讓 AI 親自「讀」圖片內容來判斷是否符合資格。
AI 資格核對（開始執行資格核對與生成公文）
  • 把「門檻規範」＋「應徵者資料」＋「附件圖檔／PDF」一起包成結構化的 Prompt，送給 Gemini API。
  • AI 被要求：嚴格對照門檻逐項判斷是否「完全符合」；若應徵者仍在職會自動換算至今年資；人資手動註記的年資可直接採信；掃描附件要親自用視覺能力閱讀。
  • AI 回傳結構化 JSON（是否通過／理由標題／詳細理由／公文文字），前端依此顯示核對結果矩陣，並自動切到對應公文。
公文自動生成
  • 若「符合資格」：自動產出符合台灣公文標準格式的簽呈草稿（主旨／說明一二三／擬辦），包含學經歷敘述、成果亮點、經費支應來源等段落，人資只要微調後送簽即可，一個按鈕就能複製全文。
  • 若「不符合資格」：自動產出補件通知草稿，具體列出缺漏項目（例如「未檢附推薦信」）。
三分頁檢視結果
  • 01. 資格核對矩陣（通過／不通過＋理由）
  • 擬聘簽呈／補件函（可一鍵複製）
  • 去識別化方框（可預覽、微調、下載）

右上角小視窗設定個人 Gemini API Key，存在瀏覽器 LocalStorage，沒有 Key 時系統會提示，並停用 AI 核對功能（但基本頁面仍可操作）。

技術架構

  • 純前端（No Backend）：所有邏輯（HTML/CSS/JS）都在瀏覽器執行，不需要自己架設伺服器或資料庫，部署成本極低（可放在任何靜態網站空間）。
  • 雙軌判斷邏輯：
    • 正規表達式（Regex）—— 用於個資去識別化這種「格式固定、規則明確」的任務，快、免費、不用等網路。
    • Gemini API（LLM）—— 用於「語意理解」這種難用規則寫死的任務，例如判斷履歷內容是否「實質符合」某個模糊的資格條件、閱讀圖片辨識證照內容。這是典型的「規則引擎＋AI 引擎」混合式（Hybrid）設計，各司其職，避免所有事情都丟給 AI 造成成本高、不穩定，或都用規則造成沒有彈性。
  • 樣式（CSS）：Tailwind CSS，已由 CDN 即時編譯改為 CLI 本機建置的正式版，減少執行期效能開銷與外部依賴。
  • 模組化：HTML（結構）、app.js（邏輯）、style.css（自訂樣式）、tailwind.css（工具類樣式）分離，方便日後維護與版本控管。

AI工具便利性與使用依賴傾向之探索性研究

以「便利性認知 → 使用頻率 → 依賴傾向」為核心路徑，結合科技接受模式（TAM）與近期 AI 成癮質性研究，用自編五構念問卷初步檢驗生成式 AI 工具便利性是否可能透過提高使用頻率，間接強化使用者依賴傾向，並延伸至拖延、專注力下降與認知卸載等後果變項。

研究動機

生成式 AI 對話工具（ChatGPT、Claude、Gemini）因「有求必應」的互動特性大幅降低使用者取得資訊、完成任務的時間與心力成本。這種高便利性提升了效率，卻也逐漸引發學界對「AI 依賴」與「問題性 AI 使用」的關注。國際研究已開始累積實證基礎——CHI 2026 的質性研究提出「AI 精靈現象」（使用者只需付出極小努力即可精準獲得任何想要的結果，是驅動依賴的核心機制），2026 年的回顧性文獻也系統整理出 AICD、PUCAI-6、GAA-3 等測量依賴傾向的量表工具。但國內針對此現象的量化實證資料仍相當有限，尤其鮮少有研究進一步檢驗「便利性認知」如何透過「使用頻率」的中介效果導致「依賴傾向」的形成路徑，更遑論探討此依賴是否會弱化使用者的自主查證與批判性判斷。

研究者本身具備醫務管理學系背景，長期關注醫療產業之數位轉型議題，並觀察到醫療從業人員工作步調快、決策壓力大，對 AI 工具的便利性可能有更顯著的吸引力與更高的依賴風險——這也是本研究將「職業別」納入分析、特別關注醫療相關工作者的動機來源。

理論基礎

  • 科技接受模式（TAM, Davis, 1989）：核心構念「認知易用性」（Perceived Ease of Use）與本研究「便利性認知」高度呼應，但本研究進一步追問：當易用性被推向「幾乎不需付出任何努力」的極致，是否反而弱化使用者自主查證與獨立思考的動機——這是既有 TAM 理論尚未充分回答的問題，也是本研究的核心切入點。
  • AI 精靈現象（AI Genie Phenomenon, Shen et al., 2026）：質性研究歸納出三種成癮性 AI 使用類型（逃避式角色扮演、擬社交陪伴、認知兔洞），其中「認知兔洞」──使用者持續且強迫性地向 AI 提出開放式問題，並將此行為自我合理化為具生產力的探索──與本研究主題最相關，其核心誘因為「資訊尋求」，高好奇心者為高風險族群。
  • 依賴量表發展脈絡：AICD 量表（Zhang et al., 2025）率先以 8 題項量化情感與行為層面的依賴；其後的 PUCAI-6、GAA-3 進一步借用行為成癮理論（顯著性、失控感、耐受性、戒斷不適等）操作化，為本研究自編問卷的構念劃分提供理論基礎。

研究問題與假設

編號研究問題對應假設
RQ1便利性認知是否與使用頻率有關？H1：便利性認知越高，使用頻率越高
RQ2使用頻率與依賴傾向是否正相關？H2：使用頻率越高，依賴傾向分數越高
RQ3依賴傾向是否與拖延、專注力下降有關？H3：依賴傾向越高，拖延與專注力下降程度越高
RQ4依賴傾向是否與自主查證／獨立思考頻率負相關（認知卸載）？H4：依賴傾向越高，查證與獨立思考頻率越低
RQ5不同職業別在依賴傾向上是否存在差異？H5：不同職業別在依賴傾向分數上存在顯著差異

研究架構以「便利性認知」為自變項，「使用頻率」為中介變項，「依賴傾向」為核心依變項，並延伸檢驗依賴傾向與「拖延/專注力下降」「認知卸載」兩項結果變項的關聯；「職業別」則作為分組比較變項。

研究方法

  • 抽樣：以目前有使用 AI 對話工具之成人為母體，採便利抽樣與滾雪球抽樣，透過社群平台與人際網絡發放線上問卷，回收有效問卷 55 份（非隨機抽樣，結果不宜推論至母體）。
  • 研究工具：自編結構式問卷，分六大部分——基本資料、便利性認知（5 題）、使用頻率（3 題）、依賴傾向（6 題）、拖延與專注力自評（3 題）、查證與獨立思考頻率／認知卸載（6 題，含 2 題反向題）。第二至六部分採 Likert 5 點量表，題項係參考文獻構念邏輯自行編寫，非直接翻譯或複製既有量表。
  • 資料分析：Excel 整理 + Python 統計套件，依序執行描述性統計、Cronbach's α 信度分析、Pearson 積差相關分析（檢驗 H1–H4）、單因子變異數分析 One-way ANOVA（檢驗 H5）。
  • 研究倫理：問卷首頁說明研究目的、資料用途與匿名性，自願參與可隨時中止，不蒐集姓名、聯絡方式等可識別身分資訊，結果僅用於學術研究與升學申請，不做商業使用。

研究結果摘要

樣本特性：n = 55，年齡 18–52 歲（M = 31.2, SD = 5.9），以 27–34 歲青壯年為主；女性 74.5%、男性 21.8%、不透露 3.6%；職業重新歸類為醫療相關工作（n=13）、資訊/科技業（n=10）、其他（n=26，含設計、金融、行政、製造、服務業等）；87% 以上填答者每日手機使用超過 3 小時，最常使用之生成式 AI 工具以 ChatGPT 占絕大多數。

信度：五大構念之 Cronbach's α 均高於 0.7 學術門檻（便利性認知 .809、使用頻率 .863、依賴傾向 .875、拖延專注力 .907、認知卸載 .741），顯示自編問卷具良好內部一致性。

研究方法嚴謹度與倫理評估

目前設計中「做得不錯」的地方：

項目說明
完整的信度檢驗五大構念 Cronbach's α 皆超過 0.7 門檻，且逐一列出而非只報告總體信度，顯示每個構念的測量品質都經過檢視，不是只看整份問卷的表面一致性。
假設檢定方法對應正確連續變項間關聯用 Pearson 相關（H1–H4），類別變項的組間比較用 One-way ANOVA（H5），統計方法與資料型態相符。
反向題設計並有明確處理認知卸載構念中的 C4、C6 為反向題，且說明「計分前進行反向轉換」，顯示對測量工具設計的細節有掌握，而非直接假設所有題項方向一致。
誠實揭露方法限制樣本規模、抽樣方法（便利抽樣、滾雪球抽樣）、性別比例失衡、職業分組異質性、共同方法變異、橫斷面設計無法確立因果，五項限制逐一列出，且明確標示「僅反映樣本內關聯趨勢，不宜推論至母體」。
研究倫理有基本把關問卷首頁說明研究目的、匿名性，不蒐集可識別身分資訊，結果不做商業使用，符合學術問卷的基本倫理規範。
自編題項而非直接套用既有量表題項參考 AICD、PUCAI-6、GAA-3 等量表的構念邏輯自行編寫，而非直接翻譯或複製，避免了未經授權使用他人量表的智慧財產與方法論爭議，但也因此犧牲了跨研究比較的直接可比性（見下方風險欄）。
需要留意的風險與建議改善方向
風險 / 限制說明建議改善方向
便利抽樣＋滾雪球抽樣的代表性風險樣本很可能集中在研究者的社交網絡內，女性占 74.5%、年齡集中在 27–34 歲即為此效應的直接證據，結果無法推論至一般 AI 使用者母體。論文已誠實標示此限制，後續研究可採用分層隨機抽樣，或至少在描述性統計階段與官方人口統計數據比較樣本代表性落差的方向與幅度。
自編量表未經正式效度驗證題項雖參考既有量表構念邏輯，但屬自行編寫，只做了信度（內部一致性）檢驗，未進行效度分析（如驗證性因素分析 CFA、與既有量表的收斂效度比對），無法確認測到的是否真的是「便利性認知」「依賴傾向」等理論構念，而非其他相近概念。後續研究可加入探索性或驗證性因素分析，或至少與 AICD 等已驗證量表做部分題項的收斂效度檢定，強化構念效度的證據。
中介效果只做相關分析，未做正式中介檢定研究框架設定「便利性認知 → 使用頻率 → 依賴傾向」為中介路徑，但統計上只分別檢驗 H1（便利性認知-使用頻率）與 H2（使用頻率-依賴傾向）兩段相關，並未做正式的中介效果檢定（如 Baron & Kenny 步驟法、Bootstrap 中介分析、結構方程模型），嚴格來說目前的證據只能說「兩段路徑各自顯著」，還不足以宣稱「使用頻率確實中介了便利性認知對依賴傾向的效果」。樣本量足夠時可用 PROCESS macro 或結構方程模型做正式的中介效果檢定，並報告間接效果的信賴區間。這是本研究在方法論上最值得留意、也是最容易在口試被追問的一點。
共同方法變異（Common Method Bias）所有變項（便利性認知、使用頻率、依賴傾向、拖延、認知卸載）皆以同一份自陳量表、同一時間點測量，構念間的相關可能部分來自測量方法本身造成的系統性膨脹，而非真實的構念關聯。論文已在研究限制中揭露此問題；後續可考慮時間隔開測量（例如先測便利性認知，一段時間後再測依賴傾向），或加入客觀行為指標（如 AI 工具實際使用紀錄）與自陳量表互相佐證。
相關不等於因果，橫斷面設計無法排除反向因果例如 H2 檢驗「使用頻率 → 依賴傾向」，但同樣合理的替代解釋是「本來就依賴傾向較高的人，才會有更高的使用頻率」，橫斷面資料無法區分兩者何者為因、何者為果。論文已誠實承認此限制並建議縱貫性研究設計。若要在口試中被問及，可準備清楚說明為何本研究只宣稱「關聯」而非「因果」。
年齡極端值的槓桿效應樣本雖以 27–34 歲為主，但涵蓋 18–52 歲，在僅 55 份的小樣本下，一兩筆極端值可能對相關係數與 ANOVA 結果產生不成比例的影響。論文已提出可做敏感度分析（移除極端值後重新計算，比較結果穩定性）的後續建議，若時間允許可在正式提交前補做這一步，結果會更站得住腳。
職業分組的「其他」類別異質性過高「其他」組合併學生、金融、行政、製造、服務業等差異很大的職業，組內變異被稀釋後，可能低估或誤判職業別與依賴傾向的真實關聯。若後續擴大樣本，應盡量維持職業分類的同質性，或改用「工作壓力/決策強度」等連續變項取代粗略的職業類別分組。
反向題比例偏低（僅 2/6）認知卸載構念 6 題中只有 2 題反向，對防止填答者不經思考、一路勾選同一端點（default responding）的效果有限。後續量表設計可提高反向題比例，或加入注意力檢核題（attention check item）過濾隨意填答的問卷。

系統定位

這是給研究中心主任辦公室使用的經費管理工具。中心主任會因為業務需要，在多個不同的經費來源（醫院費用、院內計畫、各會計代號的研究計畫、中心零用金、小組聚餐）之間產生支出，其中一部分是主任先自掏腰包墊付、事後由中心或學校歸還。

原本的作業方式是 Excel 加上紙本單據，痛點有三個：

  1. 經費來源分散，每一筆錢屬於哪個會計代號要靠人記。
  2. 墊款與歸還的時間差，5 月墊的錢可能 6 月才入帳，跨月之後 Excel 很難正確歸戶。
  3. 累計未歸還金額算不清楚，常常要回頭翻好幾個月的表才知道目前總共欠主任多少。

系統把這三件事自動化：記帳時標注款項性質，系統自動判斷該不該計入欠款，並持續維護一個「目前未歸還總額」。

這三者在會計意義上完全不同：代轉是「主任沒花錢」，自行吸收是「主任花了錢但不追討」，兩者都不算欠款，但把它們合併成一類會讓帳面失去可追溯性。獨立成三個選項，是為了讓「主任實際自掏腰包的總金額」與「中心應歸還的總金額」這兩個數字都能被正確算出來。

跨月沖帳機制
  • 選擇「主任先墊付」後，會多出「已經入帳／歸還給主任」與「入帳月份」兩個欄位。
  • 入帳月份可以與費用發生月份不同：5 月墊付、6 月才匯款歸還，只要把該筆項目編輯為已入帳、入帳月份選 6 月，系統即自動把它計入 6 月的「本月已入帳給主任」。
  • 這解決了 Excel 難以處理的「一筆資料同時屬於兩個時間維度」問題——發生時點與清償時點分離。
歷年對帳（ledger.html）
  • 列出所有尚未標記入帳的墊款（僅限「主任先墊付」類型），即時計算累計未歸還總額。
  • 提供「標記已入帳」快速按鈕，可直接在對帳頁完成沖帳，不必回到各子頁面逐筆尋找——這是依照實際作業動線設計的功能，因為對帳是一次處理一批，而不是一筆一筆想起來。
  • 同時提供歷年總表。

  • 可接上免費的 Google Firebase Firestore，以「同步房間代碼」為鍵，讓手機與電腦共用同一份資料。
  • 文件中附有給非工程人員的十分鐘設定教學（建立專案、取得 config、設定 Firestore 規則、輸入房間代碼）。
  • 不設定時系統完全照原本的本機模式運作，兩種模式並存。

技術架構

  • 多頁式純靜態架構：不使用 SPA 框架，每個經費模組是一個獨立 HTML 頁面，共用 assets/app.js（資料存取與對帳計算）與 assets/style.css（韓系極簡風格視覺）。對這個規模的工具來說，多頁式反而更好維護、除錯範圍也更容易收斂。
  • LocalStorage 作為單一資料來源：全部資料以 expenseManagerData_v1 這個鍵儲存，鍵名帶版本號，為日後資料結構變更時的 migration 預留空間。
  • Firebase 為可選加值層，不是必要相依：核心邏輯不依賴雲端，接上去只是多一個同步管道。這讓系統在使用者不設定任何東西的情況下也是完整可用的。

系統定位

這是給研究中心新進同仁報到第一週使用的單一入口網。傳統做法是行政單位把座位表、報到待辦、空間使用規範、常用系統網址分散在 PowerPoint、紙本、E-mail 與口頭交代裡，新人要問好幾個人才拼得出全貌，行政同仁也要重複回答同樣的問題。這個網站把這些散落的資訊收斂成一頁式導覽，新人自己看就能完成報到流程，行政只需要在人員異動時改一個資料檔。

設計上刻意不做後端、不做資料庫：使用單位沒有維運人力，任何需要「架伺服器」的方案在這個場域都活不下來。

核心功能（依頁面區塊）

密碼閘門（gate）
  • 進站需輸入共用密碼，通過後才會解密並渲染內容。
  • 輸入一次後同分頁內不需重複輸入（存於 sessionStorage）；關閉分頁或點導覽列鎖頭圖示即鎖回。
  • 不寫入 cookie、不寫入 localStorage，密碼本身不會送到任何伺服器。
互動式座位圖
  • 兩張樓層平面圖以 SVG 手繪內嵌於 index.html，採 viewBox="0 0 1000 520" 的相對座標系，任何螢幕尺寸都等比縮放，不需準備多份圖檔。
  • 每個座位卡顯示姓名、英文名、分機／桌號，左側色線對應所屬分組（高醫師團隊、法規、NLP、影像、系統、行政、行銷、訊號、醫資組、PM 共 10 組）。
  • 人員離職時把該筆改成 { empty: true, ext: '109' } 即成空位，新人報到再改回來，不需要重畫圖。
  • 分組代表色經過調整：原簡報圖例的粉紅、淡藍、純黃縮成細色線後幾乎辨識不出來，實作時統一加深，屬於「從簡報搬到網頁時必須重新做的視覺決策」。
第一週報到待辦清單
  • 逐項條列報到事項（開通 Email、領取門禁、環境設定等），可勾選。
  • 勾選進度以 id 為鍵存在使用者自己的瀏覽器 localStorage，不上傳、不共用——這是刻意的設計決策，避免系統變成另一個蒐集個資的地方。
  • 副作用：換電腦或清快取會歸零；且維護者若更動某項的 id，等同重置該項的勾選狀態。
空間與行政規範（可篩選）
  • 規範以 cat 欄位分類（差勤／空間／資安／表單），篩選按鈕依資料自動生成，新增自訂分類只要寫新的代號即可，不用改程式。
  • 每則規範採「摘要一行＋展開後條列」的收合式呈現，避免一次倒出整份規章造成閱讀負擔。
桌上電話撥號面板
  • 以資料驅動的按鍵面板取代原本的手繪電話照片：每顆鍵是一筆 { key, ext, outside, empty }，排列順序即陣列順序，外線鍵自動加標籤，未設定的鍵顯示為不可點的空鍵。
  • 另有撥號規則對照表（校內／院內／簡碼／外縣市）。
常用系統連結牆

差勤請假、報帳等常用系統的捷徑，圖示採 Lucide icon name 設定；url 未填時點擊會跳提示，避免上線後出現無聲的死連結。

內容加密工具（build.html）
  • 獨立的離線工具頁：貼上／載入明文資料 → 輸入密碼 → 產生 data.enc.js 供上傳。
  • 維護流程被刻意設計成「編輯明文 → 重新加密 → 只上傳密文」，明文檔由 .gitignore 擋住，避免誤推到公開 repo。

技術架構

  • 純靜態（No Backend）：HTML／CSS／vanilla JS，無框架、無建置工具鏈，丟到 GitHub Pages 或內網共用磁碟直接雙擊 index.html 都能跑。
  • 資料與呈現分離：全站文案、人員、規範、連結集中在單一 data.js，app.js 只負責渲染邏輯。維護者九成的工作只需要改 data.js，不必碰程式碼——這是讓「非工程背景的行政同仁能接手維護」的關鍵設計。
  • 客戶端加密：以 Web Crypto API 實作 AES-256-GCM 加密，金鑰由密碼經 PBKDF2-SHA256 迭代 25 萬次推導。解密全在瀏覽器端完成，伺服器（GitHub Pages）自始至終只存放密文。
  • 主題化 CSS：主色等視覺變數集中在 :root（--point、--paper、--ink、--signal 等），改一處即全站連動。
  • 外部依賴僅三項：Pretendard 字體、Google Fonts、Lucide 圖示，皆為 CDN；內網若擋外連，字體會自動退回系統預設，版面仍可正常使用（graceful degradation）。

資安評估

目前設計中「做得不錯」的地方：

項目說明
內網 IP 全數移除原始資料含各座位電腦內網 IP，考量公開網域風險已整批拿掉，僅保留姓名／分機／座位。
內容加密而非僅前端隱藏常見的「假密碼」做法是用 JS 判斷密碼後 display: none，看原始碼就破功。此處內容是真的加密過的密文，沒有密碼者把 data.enc.js 整份下載走也只會拿到亂碼。

明文資料以 .gitignore 隔離從流程面防止維護者誤把未加密的人員資料推上公開 repo。
<meta name="robots" content="noindex">降低被搜尋引擎收錄的機率。
勾選進度不上傳待辦完成狀態留在使用者本機，系統本身不蒐集任何行為資料、無追蹤碼、無 cookie。
文件中主動揭露限制README 明確寫出「這道鎖擋得住什麼、擋不住什麼」，而非讓使用單位誤以為已經很安全。
